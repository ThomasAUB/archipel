# Spec — Archipel, a multi-repo Git client

This spec defines **what** the product is and **why**. The implementation path (architecture, phases, measurements) lives in [PLAN.md](PLAN.md), which refers to the feature sections below as §1–§10.

## Vision

A Git client that is **fast, light on RAM and good-looking**, designed for working on **several repos at once**, grouped into *projects*. GitKraken, Fork and SourceTree are centered on a single repo; Archipel is centered on the project: see the state of all its repos at a glance and act on them in batch.

**A project is a place, not a list.** Each project opens as its own dashboard, shaped to the work it holds: which repos show and how they are grouped, which columns and panels appear, its color, icon and window title. Switching projects should feel like walking into a different room, not re-filtering a repo list. That identity belongs to the project definition (`archipel.toml`), so the team shares it; purely personal view state (collapsed groups, layout) stays private.

**Built for the AI coding workflow.** A coding agent works across repo boundaries: in a single run it can change an app, the libs it depends on and their plugins all at once. Single-repo clients make you go through those edits one repo at a time. Archipel shows **all the edits of a run together**: the dashboard (§3) shows which repos changed, the multi-repo commit (§4) lets you review the staged files of every touched repo, and you commit the whole change set in one pass. Reviewing and landing what the agent did across the project is a first-class flow, not a chore repeated per repo.

**Target user:** a developer juggling N related repos (app + libs + plugins, microservices, a product split across repos, …), often with an AI coding agent editing several of them at once.

## Non-goals (v1)

- No hosting, no built-in PR review (v1: links to GitHub/GitLab only; deeper forge integration is §8, P2).
- No full code editor (the quick file edit and the merge view only edit one file in place).
- No web / in-browser WASM version: a browser has no filesystem access and cannot run `git`.

## Features

Priority: **P0** = MVP, **P1** = v1, **P2** = later.

### 1. Projects (groups of repos) — P0
- A project = a name + a list of local repos.
- Add repos by manual selection **or** by scanning a parent folder (automatic `.git` detection) **or** by cloning from a URL (several at once, any URL `git clone` accepts, no forge account needed) **or** by creating one in a local folder (`git init`, new or holding files already; first branch named or Git's default; the folder's files optionally committed as "Initial commit"). Refused in a folder already a repository or inside one.
- The definition is stored in a readable file (`archipel.toml`), so it can be versioned and shared with the team.
- P2: import from submodules, `repo` manifest, VS Code workspace.

**The project file is strictly cross-platform — P0**
> Implemented except: a repo on another Windows drive is still written as an absolute path, and names are not yet checked for portability.

An `archipel.toml` written on any OS opens unchanged on Windows, Linux and macOS, and saving it from another OS produces no spurious diff.
- UTF-8 TOML; written with LF line endings and no BOM, read with either line ending and with or without a BOM.
- Repo paths are relative to the file's folder and written with `/`; `\` is accepted on read. An absolute path is never written: a repo with no relative path from the file (e.g. another Windows drive) cannot be added to a shared project file, and the user is told why.
- Paths and names must be valid on every OS: no characters or names Windows forbids (`<>:"|?*`, `CON`, `NUL`…, trailing dot or space), and no two entries that differ only by case. Such an entry is refused when added, and reported (not silently dropped) when loading a file written by hand.
- Nothing OS-specific is stored: no drive letters, environment variables, shell commands or platform-only settings. Anything machine-specific belongs in the personal state kept in the user data dir.
- Output is deterministic: same key order, repo order and formatting on every OS, so the file only changes when the project does.

**Launch from a directory — P1**
> Implemented: `archipel <dir>`. Not yet: the file-manager "Open with Archipel" entry (needs the installer, see Packaging in the README).

- `archipel <dir>` (or `archipel .`, or "Open with Archipel" from the file manager) opens the app on that directory.
- If the directory holds an `archipel.toml`, that project is opened.
- Otherwise the repos around are detected automatically and added to the list: the directory is scanned downward (same depth-limited scan as "scan a parent folder"); if it is itself inside a repo, the scan starts from the outermost enclosing repo root.
- The result is written as an `archipel.toml` at the scanned folder (the directory, or the outermost enclosing repo root); launching again from the same directory opens that file.
- No confirmation dialog: the list appears immediately and fills in as the scan progresses (cancellable).

**Hidden repos — P1**

- Any repo of a project can be hidden when it isn't wanted (context menu or keyboard), individually or in batch.
- Hidden repos disappear from the dashboard, graph switcher, batch actions and multi-repo commit; they are neither watched nor refreshed (saves CPU and RAM).
- A "show hidden repos" toggle lists them, dimmed, with an "unhide" action.
- Hiding is a personal choice: stored in the personal state in the user data dir, never in the shared `archipel.toml`. Removing a repo from the project stays a separate, explicit action.

**Repo categories — P1**

- Any repo can be given a category (a free-form name: "apps", "libs", "plugins", …), individually or in batch, from the repo context menu or the action palette; picking an existing category or typing a new one, or clearing it.
- The sidebar groups repos by category under collapsible headers (name + repo count), categories sorted by name, repos keeping project order inside each group; repos without a category come last under "Uncategorized". With no category at all, the sidebar stays a flat list.
- A category header's context menu renames the category (on every repo using it; an existing name merges into that category) or removes it (its repos become uncategorized, they stay in the project). A category exists only while a repo uses it.
- Categories describe the project, so they are stored on each repo entry of the project definition (`category = "libs"` in `archipel.toml`) and shared with the team. Which groups are collapsed is personal (user data dir).

### 2. Project switching — P0
- Fast keyboard switcher (`Ctrl+P` style), plus a recent-projects list.
- Each project keeps its own UI state (selected repo, filters, layout).
- Switch in < 200 ms (state cached, refreshed in the background).

**Several instances side by side — P1**

- Several projects / directories can be open at the same time, each in its own window, behaving as an independent instance (own selected repo, filters, layout, background refresh).
- **One process, many windows:** launching `archipel <dir>` while Archipel is running hands the request to the running process (local IPC), which opens a new window. An extra window costs only its project's data, not another GPU context, font set and caches — consistent with the RAM target.
- Opening a directory / project that is already open focuses its window instead of creating a duplicate.
- **Going to another window from the keyboard:** the project switcher (`Ctrl+P`) lists the projects of the other windows first, most recently active first, so `Ctrl+P`, `Enter` goes back to the previous window. ``Ctrl+` `` / `Ctrl+F6` activate the next window in opening order (with `Shift`, the previous one), wrapping around; the `F6` pair works on keyboard layouts where the backquote is a dead key.
- Shared state (settings, recent projects, on-disk caches) stays consistent when several windows write to it concurrently.
- **Recent projects on the app icon:** right-clicking the taskbar button (Windows jump list, "Recent Folders") or the Dock icon (macOS, recent items) lists the folders of the most recently opened projects (as many as the switcher's recent list); picking one opens that project as `archipel <dir>` does, in the running process. The Windows jump list also has a "New Window" task. An entry removed from the Windows jump list stays out of it until Archipel restarts. macOS shows the list only for an app bundle declaring folders as documents (macOS packaging is not done yet); Linux has no such list.

**Recognizing a window at a glance — P1**
> Implemented except the taskbar badge (it needs a native Windows API call, i.e. an `unsafe` exception and an ADR).

- **Per-project accent color:** derived automatically from the project path (stable across launches), overridable by the user. Shown as a thin colored band at the top of the window, and on the selection and project name; built on the theme engine's accent-derived palette. An optional per-project background tint, also shared through the project file, mixes a percentage of the accent's hue into the window's surfaces while keeping the theme's lightness (lifted slightly towards the text only when a very dark or very light background cannot hold the color), so it suits light and dark themes alike and every user keeps their own theme.
- **Project name first in the window title** (`myproject — Archipel`), so the taskbar, Alt+Tab and window lists stay readable when titles are truncated.
- **Taskbar badge:** a small dot in the project color with its initials, overlaid on the taskbar icon (native overlay on Windows; best effort on Linux), to tell grouped windows apart.
- **Optional project icon:** an emoji, or an image file (PNG, SVG…) kept relative to `archipel.toml`, chosen by the user, shown next to the name in the project switcher (and in the title bar for an emoji, since titles are text).
- Color and icon belong to the project: stored in the project definition, so `archipel.toml` shares them with the team (a new file gets the automatic color written in it).

### 3. Project dashboard — P0
A minimal view, one row per repo:

| Column | Content                                            |
| ------ | -------------------------------------------------- |
| Repo   | name + path                                        |
| Branch | current branch (or detached HEAD)                  |
| Sync   | ahead / behind upstream, conflict forecast badge   |
| Changes| modified / staged / untracked file counts, stashes |
| Version| tag when HEAD is exactly on one, else the branch (short commit if detached) |
| Fetch  | time of last fetch                                 |

- Live updates through a file watcher (no expensive polling).
- Filters: "dirty repos only", "behind remote", …
- Category filter (once the project has categories): a single dropdown button in the toolbar, so many categories do not crowd it. Its label sums up the selection ("Category: all", "Category: libs", "Category: libs +2"); its menu is a checklist of the categories, plus "Uncategorized" when some repo has none, and "Show all categories" to clear the selection. The menu stays open while ticking, so several can be selected; selecting several shows the repos of any of them; it combines with the other filters (AND). The selection is personal UI state and follows a category rename (a removed category's selection becomes "Uncategorized").
- Quick edit: a click on a repo opens a pane beside the rows for the everyday edits, without opening the repo tab: fetch / pull / push (a repo without remote is published first, §8; a branch without upstream gets one on the remote: the only one, or, when the repo has several, the one picked in a row offering them, `origin` first, e.g. to push to a fork; Commit and push takes the default remote, `origin`), stash / pop, undo / redo, create or switch branch, stage / unstage / discard files, commit (amend, commit & push), continue / abort a merge, rebase, cherry-pick or revert in progress.
- Change remote URL: the repo row menu (one repo), and in the repo tab the menu of a remote branch (its remote) or of the REMOTE header, asks for the new URL of its remote, filled with the current one (the remote to change is picked first when there are several; a repo without remote gets an `origin`). It runs `git remote set-url` (or `git remote add`) on the repo's write queue, for the repo and all its worktrees, then reads the forge status again. Configuration only: not undoable, no network. A separate push URL (`remote.<name>.pushurl`) is left in place, and said so.
- Batch actions: **fetch all**, pull all, check out the same branch on every repo, create a branch/tag on several repos.
- Background fetch (`auto_fetch_secs`, default 10 min, 0 = off): one repo at a time, spread over the interval, open and selected repos first. It never gets in the way: skipped when the repo is busy, cancelled when the user writes to it, absent from the operations drawer. A repo whose fetches bring nothing is fetched less and less often (up to 8× the interval), a failing one waits the longest; open and selected repos are exempt and never wait longer than the interval, and the window getting focus fetches those not fetched for 2 min; a manual fetch resets the repos it covers. A fetch that moves no ref only updates the "last fetch" time.
- Conflict forecast (`conflict_forecast`, default on): after every refresh that moves `HEAD`, the upstream or the pull request (a fetch, a commit, a checkout), Archipel checks in the background whether the current branch would conflict with its **upstream** (what a pull would do: only when it is behind it and has commits of its own, else a pull fast-forwards) and with the **target of its open pull request**, or the remote's default branch when there is none (not when on that branch, nor when it is the upstream). `git merge-tree --write-tree` merges in memory: the worktree, the index and the refs are never touched. The upstream check follows `branch.<name>.rebase` / `pull.rebase`: a rebase replays the local commits one by one (merges and commits already upstream left out, as `git rebase` does) and stops at the first that conflicts — it can conflict where a merge does not; past 100 commits a merge is checked instead. The target check is a merge, as the forge does. The Sync column shows a **"will conflict · n"** badge (n distinct files); hover lists the files of each check, with the branch and the strategy checked. Local changes are not part of it, but when a pull would change locally changed files the badge reads **"touches n modified"** instead (listed on hover). The **Will conflict** filter chip lists only those repos; the Quick Edit Header and the Repo Toolbar show the same badge. Results are cached by the commit ids of both sides and the strategy, and only recomputed when one moves; one check runs at a time, never in the operations drawer, giving way when the repo is busy.
- Update check (`update_check_hours`, default 24, 0 = off): 30 s after the first window opens, then at that interval, the latest GitHub release of Archipel is compared with the running version; a newer one shows an "↑ Update x.y.z" badge in the status bar, × hides it until the next release. A click installs it in the background: the release archive for the platform is downloaded (the badge shows the share), checked against the release's `SHA256SUMS.txt`, unpacked with the system `tar` and put in place of the running binary (on Windows the running one is moved aside as `archipel.exe.old`, deleted at the next start). The running process is untouched: the new version runs from the next launch, or at once with the badge's **Restart to update** (projects saved, the last one reopened; the new process takes over the single-instance listener with `--after-update`). A failure (no archive for the platform, bad checksum, binary not writable) shows **Update failed** with the reason on hover, and a click tries again. Right-click on the badge opens the release page. Failures are silent (debug log) and retried after an hour. Builds updated by a package manager are compiled with `ARCHIPEL_NO_UPDATE_CHECK` set: no check at all.

### 4. Multi-repo commit — P0
- Pick the repos to commit (pre-checked: those with changes).
- One message applied everywhere; preview of the staged files per repo.
- Partial-failure handling: if a hook fails on one repo, show a clear report (committed / failed) and allow a retry — no fake "all or nothing".
- Options: push after commit, ticket prefix (e.g. `JIRA-123`; after a Conventional Commits `type(scope): ` header when the message has one), message templates.

### 5. Repo view + graph — P0
- Commit graph, diff, staging per file / hunk / line.
- File browser: **Files** in the toolbar swaps the details pane for the repo's file tree, at the selected commit or stash, or in the working copy (uncommitted-changes row selected, or nothing selected); it follows the selection. A filter box narrows it to the files matching fuzzily; ↑↓, Page Up / Down, Home / End move, → / ← open or close a folder, Enter opens, Esc closes. A file opens read-only in place of the graph, highlighted and searchable; a file goes to the quick file edit on **Edit** or a double-click, at that line, and shows again, reloaded, once saved or cancelled. At a commit or stash, Edit selects the uncommitted-changes row first and edits the file as it is on disk (local changes kept, never that commit's version): saving makes an uncommitted change. An image (PNG, JPEG, WebP, GIF, BMP, TIFF, ICO, PNM, SVG; up to 32 MB) shows as its image, decoded off the UI thread, over a checkerboard showing transparency, fitted to the pane, with its size, format and weight; an SVG can show its source instead (**Source** / **Image**). A Markdown file (`.md`, `.markdown`…) shows rendered (GFM: tables, task lists, highlighted code blocks), with **Source** / **Rendered** to switch (kept from one file and commit to the next): its ```` ```mermaid ```` blocks are drawn as diagrams in the theme's dark or light colors, without a browser (a diagram that does not parse shows its source and the error); its images are read from the same commit or the working copy, never from the network; a link to a heading scrolls to it, one to a repo file opens it (a folder: its README), at its heading if any, a web or mail link opens in the browser; raw HTML is not run. Other binary files and text files over 4 MB are not shown; submodules are listed, not opened.
- File history and blame: an open file shows as itself (**File**), as the selected commit's change to it (**Change**), or with who last changed each line (**Blame**); the choice stays from one commit to the next. Blame puts a gutter before the lines naming, for each block, its commit, author and age, with a bar shaded from the oldest lines to the newest (uncommitted lines in the working copy get the dirty color); hovering a block shows its commit's message, author and date, a click selects the commit, Alt+click the commit before it (in the file as it was named there), to step past a reformat or a move. **Ignore whitespace** (`-w`) and **Detect moves** (`-M -C`) refine it. **History** swaps the file tree for the commits that touched the file, newest first, renames followed, read 200 at a time (**Load more**); a click selects the commit and shows its change to the file (in Blame, the blame there). A one-file diff (a commit's file, or a working-copy file) has **History** and **Blame** buttons opening the file browser on it. Loads run off the UI thread and are cancelled when another file, commit or mode is shown.
- Full file in a diff: **Full file** / **Changes only** in an open diff's header (commit, stash, multi-commit selection, working copy; repo tab and dashboard quick edit pane) switches between the hunks alone and the whole file, the unchanged lines between and around the hunks shown as context, read off the UI thread from the file's new version (the commit, the newest selected commit, the file on disk for unstaged, the index for staged); the changes show meanwhile. Added and removed lines keep their colors and markers, hunk headers and their stage / unstage / discard buttons stay, line picks, text selection and double-click to edit work on every line; Copy as patch leaves the lines outside the hunks out. The whole file opens scrolled to its first change; the choice carries over to the next diff. Added, deleted, binary and truncated files, and files over 4 MB, show their changes only.
- Image diff: a one-file diff (commit, stash, multi-commit selection, or working copy, in the repo tab and the dashboard quick edit pane) of a binary image shows the image before and after instead of "Binary file", decoded off the UI thread; the all-files diff keeps the note and says to open the file. Before / after are the commit's first parent and the commit (the oldest selected commit's first parent and the newest one for a multi-commit selection), the index and the file on disk (unstaged), `HEAD` and the index (staged). Both share one scale: they sit top-left on a canvas as large as the larger one, fitted to the pane at first, each labelled with its size, format and weight. An added or deleted image shows alone. Once both are read, chips pick how they are compared (the choice carries over to the next image diff of the view): **Side by side**; **Swipe**, one canvas with the image before left of a split and the one after right of it, the split following a press or drag on it; **Onion skin**, the image after over the one before at the opacity a slider sets; **Blink**, the image after, the one before while **Hold for before** is pressed, or each in turn every 500 ms with **Auto**; **Difference**, `|before − after|` per channel and pixel, computed off the UI thread (black where nothing changed; a pixel only one image covers counts as changed), **Amplify ×4** on by default, with "N px changed (x %)". Overlaid, both sizes show above the canvas, and "sizes differ, aligned top-left" when they do. An SVG is rasterized, so every mode applies to it. A text SVG diff shows its lines, with **Images** / **Text** to switch.
- Image zoom (image viewer and image diff): the scroll wheel (or a pinch) zooms around the pointer, from 100 % (or the fit, if smaller) up to 6400 % (or the fit, if larger); zooming past the fit stops on it. Once zoomed, a drag pans, as far as the image still covers the pane (the middle button in **Swipe**, where a left drag moves the split). The bar shows the zoom's percentage; **Fit** fits the image again. Both sides of an image diff zoom and pan together, and the zoom carries over to the next image diff of the view.
- Quick file edit from a working-copy diff (repo tab and dashboard quick edit pane): **Edit**, or a double-click on a line, swaps the diff for a code editor on the file, at that line. Ctrl+S saves and goes back to the reloaded diff; Esc goes back without saving (a second Esc when there are unsaved changes). A save is refused, the editor staying open, when the file changed on disk since it was opened. Line endings (CRLF) are kept; binary, non-UTF-8 and very large files are not edited there.
- Merge view: a conflicted file opened from the staging panel (repo tab and dashboard quick edit pane) shows, in place of its diff, **Ours** and **Theirs** (the file as each side has it) side by side above the **Result** (the file itself, conflict markers included, freely editable). Conflicting lines are picked with the mouse in Ours and Theirs: a click picks or drops a line, a drag gives the lines it crosses that state, Shift+click extends from the last line clicked, a double-click (or the block's box: none / some / all) takes or drops the whole block of that side. Once the mouse is released the conflict is rebuilt in the Result with the lines picked, in file order, the side picked first leading (**⇅ Swap order** flips them); dropping every line brings the conflict markers back. Picked lines are tinted green with a bar in the gutter; open conflicts are tinted, the current one framed and scrolled to. The toolbar names it ("Conflict 2 of 5 · 3 left"), moves through the conflicts left (↑ / ↓, or Alt+↑ / Alt+↓) and resolves it with **Ours** (Alt+←), **Theirs** (Alt+→), **Both**, **Base** when the markers hold it (`diff3` / `zdiff3` styles) or **None**, then moves to the next one; **All left: Ours / Theirs** resolves every conflict left. Each pick is an edit of the result (Ctrl+Z in it takes it back); the conflicts are followed through hand edits of the result. The side names come from the markers (`HEAD`, the merged branch or commit). Ctrl+S saves the result without resolving; **Mark resolved** (Ctrl+Enter) writes it and stages it, refused while conflict markers are left, or when the file changed on disk since it was opened, then opens the next conflicted file (with none left, the status line says to Continue or commit). Resolving is undoable: the undo brings the conflict back in the index, and the file as it was before. A file a side deleted is resolved by keeping the other side's result or **Delete file**; a binary, non-UTF-8 or over-4 MB file is resolved whole (**Keep ours**, **Keep theirs**, **Delete file**). An external tool replaces the view when picked with **Set merge tool…**.
- Conventional Commits helper in the commit box (repo tab and dashboard quick edit pane): chips above the message, one per type (`feat` `fix` `refactor` `docs` `test` `chore` `perf` `build` `ci` `style` `revert`, or the project's `conventional_types`), set or replace the `type(scope)!: ` prefix of the subject, keeping the rest of the message; the type of the subject is highlighted, typed by hand or not, and a click on it removes the prefix. Once the subject has a type, **!** marks a breaking change (`feat!:`) and scope chips insert `(scope)` (a click on the active one removes it): scopes of the staged files first (a history scope naming one of their folders, else their first folder that is not a mere container like `crates/` or `src/`, without the repo name prefix: `crates/archipel-ui/…` gives `ui`; `.github/` gives `ci`), then those of the recent history, most used first. A muted line under the message warns, never blocking the commit, when the subject is not `type(scope)!: description` or its type is not in the list, the description is missing, starts with a capital letter (not an all-caps word like `JIRA-1`) or ends with a period, the subject is over 72 characters, or the body follows it without a blank line. `conventional_commits` in `archipel.toml` shows the helper `on`, `off`, or (`auto`, the default) when most of the repo's 100 most recent commits (merges left out, at least 3) follow the convention; those commits are read off the UI thread when `HEAD` moves and cached per repo. Amend pre-fill and reword are unchanged: the chips act on whatever message is in the box. With a ticket prefix (§4), the ticket goes after the header (`feat(ui): JIRA-1 …`).
- Ignore from the staging panel: an unstaged file's ignore button opens a dialog proposing patterns built from it, narrowest first: the file itself, every file of that name, every file of its extension, those directly in its folder, then each of its folders (an untracked folder: itself, every folder of that name, its parents). Picking one fills an editable pattern field; **Add to .gitignore** (or Enter) appends it as a line of the `.gitignore` at the repo root, created when missing, in the file's line ending, unless it is already there. Names are escaped so they match literally; a tracked file gets a note that Git keeps tracking it.
- Virtualized graph: smooth even with 100k+ commits.
- Everyday repo actions: commit / amend, branches (checkout, create, rename, delete, set upstream), tags, stashes, fetch / pull / push, reset, revert, continue / skip / abort a merge, rebase, cherry-pick or revert in progress, from the toolbar whatever is selected; Undo (Ctrl+Z) while one is in progress aborts it.
- Conflicts open by themselves: when a write or network operation of Archipel (pull, merge, rebase, cherry-pick, revert, stash pop, continue…) leaves a repo with conflicted files where it had none, or moves `HEAD` and stops on conflicts (a rebase or cherry-pick continued onto its next conflicting commit), what **Set merge tool…** (action palette) picked opens. By default the **built-in merge view**: the repo tab opens on the uncommitted changes with the first conflicted file in the merge view. Or an external tool: **Git's merge tool** (`merge.tool`) or one of the tools Git knows (installed first; any name can be typed), run with `git mergetool` on every conflicted file on the repo's write queue, the repo refreshed when it closes; closing it with conflicts left does not reopen it, and with no tool named nothing runs and a notice says how to pick one. **Resolve conflicts** (action palette) opens the same on demand. The choice applies to every window and is saved as `merge_tool` in `settings.toml` (absent: built-in, `"git"`: Git's merge tool, else the tool's name); Terminal tools (vimdiff…) cannot run without a terminal.
- Reword: a double-click on the message of a commit in the details pane edits it in place; **Save** (Ctrl+Enter) gives the commit the new message and rewrites the commits after it on top, unchanged (index and worktree untouched, undoable), **Cancel** (Esc) drops the edit. Only commits of the current branch's first-parent history can be reworded.
- Find in the graph: `Ctrl+F` in the graph opens a find bar above it, searching the whole history in the background for the typed text in the full commit messages (summary and body) and authors (case-insensitive) and as a prefix of the commit ids. Typing goes to the first match from the selected commit down; Enter / ↓ / F3 go to the next match, Shift+Enter / ↑ / Shift+F3 to the previous one, wrapping; the bar shows "n of m", the matching rows are tinted in the graph and the matched text is highlighted in their summaries and in the message of the details pane (a match in the body shows there only). Esc closes it. A reload of the graph searches again without moving the selection.
- Several commits can be selected in the graph: Ctrl+click adds or removes one, Shift+click selects the commits from the selected one to the clicked one that are in that range (the newer one and its ancestors down to the older one: commits of other branches shown in between are left out), Esc goes back to the single selection; the details pane then lists the files changed by the commits from the oldest selected one (lowest in the graph) to the newest, both included (diff from the oldest one's first parent to the newest), the commits selected in between taking no part in it, each opening in place of the graph like a commit's.
- **Cherry-pick N commits** from the graph menu of a multi-selection picks the selected commits one by one onto the current branch, oldest first, whether they follow one another or not; merge commits among them are skipped (their changes come from the merged branch's commits) and counted in the status line. Stops at the first conflict like a single cherry-pick, to continue, skip or abort.
- Squash from the graph menu of a commit of the current branch: **Squash into parent…** (the commit and its parent) or **Squash from here to <branch>…** (the commit and every one after it); on a multi-selection, **Squash N commits…** (the selected commits must follow one another, otherwise the squash is refused with the number of commits missing in between). A dialog shows the combined messages, oldest first, to edit; **Squash** (or Ctrl+Enter) makes one commit of them, authored as the oldest. Commits after the range are rewritten on top with the same content, merges included; trees are kept, so nothing can conflict and uncommitted changes are left as they are. Refused, with the reason, for a commit off the first-parent history of the current branch, a range holding a merge, or while an operation is in progress. Undoable like a rebase.
- Checkout keeps uncommitted changes: when Git refuses because they touch files that differ on the target, they are stashed, the target is checked out and they are re-applied there (staged state kept). If they conflict with the target, the target stays clean, the changes stay in an `archipel: autostash` stash entry and the status line says so; undoing the checkout switches back and pops them. Batch checkout over many repos does not autostash.

### 6. Branch drag and drop — P1
Always confirmed through a menu, never a silent action:
- branch A → branch B: *merge A into B* / *rebase A onto B* / *fast-forward*
- local branch → remote: *push*
- commit → branch: *cherry-pick*
- **Undo** for every local operation; a push gets a confirmed compensating action instead (revert or force-with-lease). Undo is refused, with an explanation, when it would lose work. Details: [PLAN.md](PLAN.md) §2.4.

### 7. Statistics — P1
> In the desktop app so far: the Branches Panel (merged-not-deleted and stale branches across repos, batch delete) and the Statistics panel (phase 1, and the language breakdown of phase 2, below). Activity and churn hotspots are also computed incrementally (`archipel-cli stats`).

Computed locally, per repo and aggregated per project. Three views in v1:
- activity over time (commits / week) per author;
- branch age, and merged branches that were never deleted;
- file hotspots by churn (lines added / removed).

Anything else waits for real usage.

**Statistics panel (phase 1).** Opened from the dashboard and the tree view: the **Statistics…** toolbar chip (the selected repos, all when none), **Statistics…** in the row menu (that repo, or the selection), the **Statistics** hover button of a tree repo node, and the `repos.stats` action. It reads the history of each repo's default branch (`HEAD` without one; worktrees stand for their repo) in the background, four repos at a time, and shows the project (all repos together) or one repo, picked with chips. Closing it cancels the reads. Charts, each with its values on hover:
- KPI tiles: commits, contributors, median commit size, median lead time to merge, unreleased commits, Git size.
- **Contribution**: share of commits and of changed lines per author (merges excluded; `.mailmap` applied, then the emails used under one name, ignoring case, count as one person), as a donut and bars; colors follow the person across repos.
- **Activity**: commits per week over the last year.
- **Commit size**: histograms of lines and files per commit; per author the median and 90th percentile, tiny (≤ 2 lines) and huge (> 1000 lines) commits; the largest commits; streaks of 3+ tiny commits in a row by one author.
- **Churn against age**: files first committed 180+ days ago and changed at least twice in the last 90 days, ranked by recent commits weighted by the log of the age, as a scatter plot and a list.
- **Lead time to merge**: for each merge on the first-parent line, the time from the oldest commit it brought to the merge, from local history alone (no forge); scatter over time (log scale), median, 90th percentile, slowest merges.
- **Tags and releases**: tags on a time line per repo, the median time between them, and the commits of the walked branch not in the latest tag (unreleased work), even when that tag is on another branch.
- **Repository weight**: size of the Git directory split into packs, loose objects and the rest; the largest blobs (and a few unreachable ones); suggestions: `git gc` (many loose objects or packs, large unreachable objects), Git LFS (blobs over 5 MiB without LFS), a shallow or partial clone (over 500 MiB of history).
- **Languages** (phase 2): the share of each programming language in the tree of the walked branch, by lines and by files, as a language bar (as on a GitHub repo page) and a list; in the project, one bar per repo besides, as long as its line count. Languages come from file extensions and a few file names (`Makefile`, `Dockerfile`, `CMakeLists.txt`…); data and prose formats (JSON, YAML, TOML, Markdown, plain text) are not counted. A `.h` header counts as C++ or Objective-C when the repo has more sources of that language than C sources. Left out: binary files (as Git tells them), vendored code (`vendor/`, `node_modules/`, `third_party/`, `external/`…) and generated files (`dist/`, `generated/`, `*.min.js`, `*.pb.go`, `*_pb2.py`, `*.Designer.cs`…), counted in a note. The `linguist-generated`, `linguist-vendored`, `linguist-documentation` and `linguist-language` attributes of the repo's `.gitattributes` (as of that commit, Git 2.40+) override these rules, as on GitHub. **Choose folders…** above the chart opens the tree of the folders holding source files (one root per repo shown), each with its lines and files: unticking a folder leaves out everything below it, and a folder ticked inside an unticked one counts again (untick the root, tick `src`: only `src`). A partly counted folder shows a mixed box; clicking it ticks it whole. **Count every folder** resets. The choice is kept while the panel is open (not saved). Each language row shows its line count. Files left out this way are counted in the note too.

### 8. Forge integration (GitHub, GitLab, …) — P2
> Implemented for GitHub (and GitHub Enterprise Server) and GitLab (gitlab.com and self-hosted): sign-in by personal access token, "Pull request" dashboard column, "CI" dashboard column (latest run of the current branch, jobs on hover), pull requests across repos, open pull requests listed per repo, assigned and merged from Archipel (now or once their CI passes), issues created, listed, closed and reopened, clone from an account, publish a new repository (ADR 0003). Not yet: OAuth device flow (it needs an OAuth application registered on each forge), Gitea / Forgejo, Bitbucket and Azure DevOps providers (links only).

Easy, low-friction integration with code hosting forges:
- Providers: GitHub, GitLab (including self-hosted), then Gitea / Forgejo, Bitbucket, Azure DevOps — each as a pluggable provider behind one small trait, so a fork can add its own without patching the core.
- Setup in a few clicks: provider auto-detected from the remote URL; sign-in by OAuth device flow or personal access token, stored in the OS keychain (never in `archipel.toml`).
- Clone from an account / organization / group: browse and pick repos, clone several at once straight into a project.
- Publish a repository that has no remote yet (one made with New…): Push on it opens the **Publish** dialog, which creates the repository on a signed-in account (the user's own namespace or an organization / group, name prefilled from the folder, description, private by default, HTTPS or SSH URL) or takes the URL of an existing empty one; it becomes `origin` and the branch is pushed there and tracked. Nothing is created for a branch without commit, a detached `HEAD` or a repo that already has a remote; when the push fails after the repository was created, `origin` stays set, so Push retries it. GitHub tokens need `repo` (classic) or Administration read and write (fine-grained); GitLab tokens `api`.
- Per-repo forge status in the dashboard: open PR/MR for the current branch, its CI status, review state.
- CI status of the current branch in the dashboard, with or without a PR: overall state and job counts in a "CI" column, every job (failures first) on hover, "Open CI run" from the row menu. While a run is going, and for a few minutes after a pull request is opened from Archipel (the forge takes a moment to register the runs), the CI is re-read every `ci_poll_secs` (20 s). After a checkout the status of the previous branch is cleared at once and the new branch is read right away, even if a read of the previous one is still going. The forge is also read again at once when the branch head or its upstream moves (a commit, a push, a fetch), however recent the last read. A run that is not for the tip of the upstream (the forge has no run for a just-pushed commit yet, or the upstream was not fetched) is shown muted, marked **·old**, with both commits on hover; it is then followed closely, as after opening a pull request, until the forge has the new run. Such a run does not count for the **CI failing** filter.
- CI failure excerpt and rerun: hovering a failing run (the CI column, the CI Badge) also shows the **last error lines** of the log of each failed job (up to 3), read on the first hover and kept for the session, with "Open the full log" and **Rerun failed jobs**; the tooltip stays open under the mouse so they can be clicked. Only the end of the log is kept (64 KiB); the error lines are found by simple rules (lines with `error`, `FAILED`, `panicked`, a non-zero exit code, plus 2 lines before and 3 after, the last groups first, 30 lines at most) that a provider can override, and the raw end of the log is the fallback. GitHub: the logs of GitHub Actions jobs (checks posted by another CI have none here), and a rerun restarts the failed jobs of each workflow run of the commit (`rerun-failed-jobs`); GitLab: the job trace, and a rerun retries the pipeline. "Rerun failed jobs" is also in the Row Menu, and **"Rerun failing CI of selected repos"** in the Action Palette is a batch action (repos whose CI does not fail are skipped; per-repo failures in the drawer). After a rerun the CI is followed closely, as after opening a pull request. Rerunning needs a token with write access to the CI: when it is missing, the error names the scope to add (GitHub: Actions read and write, or `repo`; GitLab: `api`).
- CI mark (`✓` / `●` / `✗`) after branch names in the repo view's branches panel: the current branch from its CI run, the other local and remote branches from the CI of their open PR/MR (not one from a fork). Jobs or PR on hover, click opens the run or the PR. The open PRs are read when the repo view opens and whenever the forge status of the repo changes.
- Create a PR/MR from a branch (title, description, target branch prefilled); multi-repo: one PR per repo for the same branch, linked together.
- List the open PRs/MRs of the selected repos (source → target, author, CI, review, mergeability) and merge one: merge commit, squash or rebase (GitHub; GitLab uses the project's method), optionally deleting the source branch. A second click confirms; the forge refuses if the head moved since the list was read. The repo is fetched afterwards.
- Assign a pull request: each row of that list shows its assignees and an **Assign** chip; it opens, under the row, a chip per user the pull request can be assigned to (read once per listing: GitHub's assignable users, GitLab's project members, inherited ones included) and per current assignee; **Save** replaces the assignees with the picked ones (none: unassigns all). The forge's answer is shown: a login it did not keep (GitHub drops a user who cannot be assigned, GitLab Free keeps one assignee) is named in the status line. Listing who can be assigned needs write access to the repository; without it the editor says so and still shows the current assignees. Tokens: GitHub `repo` (`public_repo` for a public repository) or fine-grained Pull requests read and write; GitLab `api` and the Developer role; when missing, the error names the scope to add.
- Merge when CI passes: **When CI passes**, next to Merge in that list, arms the merge with the same choices instead of running it now (**… in all N repos** arms the linked pull requests of the same branch across the listed repos); in the Row Menu of a repo whose current branch has an open PR, **Merge #N when CI passes…** opens that list. The forge's own auto-merge is used, so it works with Archipel closed: GitHub `enablePullRequestAutoMerge` (GraphQL; the source branch is deleted only when the repository's "Automatically delete head branches" setting is on, said when it is off), GitLab "merge when pipeline succeeds" (GitLab merges at once when the pipeline already passed). Its state is read back with the pull request: an armed PR shows **⏲ auto-merge** in the list and a `⏲` in the Pull request column (what it does on hover), with **Cancel auto-merge** in the list and the Row Menu. When the forge refuses it (setting off on the repository, missing token scope, nothing left to wait for), Archipel watches the PR itself, only while it runs and the project is open (said in the list, the column and the status line): every `ci_poll_secs` it reads the PR, and once its CI passed merges it, only at the commit whose CI passed, then fetches the repo, as a manual merge does. As with the forges' own auto-merge, a failed CI, a conflict or a new push leave it armed (the mark says why it is not merged yet: a rerun or a push can still pass); it is dropped when the PR is merged or closed elsewhere.
- Issues: **New issue…** (Row Menu, Action Palette) opens a form with a repo picker over the targeted repos (the clicked one picked), title, description (Markdown), and the repo's own labels and assignees as chips; the status line then gives the issue number, a click opens it on the forge. **Open issues** of the selected repos are listed like the open pull requests (number, title, author, labels, assignees, age) with **Open on forge** and **Close**. Close takes a reason (Completed / Not planned: GitHub `state_reason`; GitLab has none) and an optional comment, posted first; a second click confirms. An issue closed from Archipel stays listed, muted, with **Reopen** for the rest of the session. Issues go to the forge repository of the remote the row's forge status uses (a fork's, not silently its upstream's). A repo with issues disabled, or a provider without issues, is said so in the form before anything is typed. Tokens: GitHub `repo` (`public_repo` for a public repository) or fine-grained Issues read and write; GitLab `api`; when missing, the error names the scope to add. Not yet: closing the issues a merged pull request names (`Fixes #n`) when the forge did not.
- Still no built-in code review (see Non-goals): reviewing happens on the forge.

### 9. Repo dependency tree — P2

Show how the repos of a project depend on each other, as a small tree:
- Nested submodules at any depth (repo → submodule → submodule → …), with each node's state (initialized or not, pinned commit vs. checked-out commit, dirty).
- Repos of the project that are themselves submodules of another project repo are shown under their parent rather than twice.
- **Toggleable:** off by default, a single toggle shows it in the dashboard / sidebar, so the flat view stays uncluttered when nesting doesn't matter. The choice is per project UI state.
- Compact rendering (indentation + connectors), collapsible nodes; works with the dashboard filters.
- Actions from a node: init / update a submodule (recursive or not), open it as a repo, add it to the project.
- **Add submodule…** (repo row menu, action palette, `+` on the Refs Panel SUBMODULES header, which is always shown): asks for the URL, then the path (prefilled with the URL's last component, without `.git`), then runs `git submodule add` on the network queue; the new submodule and `.gitmodules` are staged, left to commit. Paths outside the working tree are refused.
- **Remove submodule…** (right-click a submodule in the Refs Panel), after a confirmation: `git submodule deinit` (without `--force`, so Git refuses when the submodule has local changes), `git rm` (the gitlink and its `.gitmodules` section; the removal is staged, left to commit), then deletes its clone under `$GIT_DIR/modules/<name>` so the same path can be added again.
- Later: other dependency sources through the same extension point (e.g. `repo` manifests, package-manager path / git dependencies).

### 11. Integrated terminal — P2
> Implemented (issue #98, ADR 0005).

- A terminal panel docked under the workspace (**Toggle terminal panel**, `Ctrl+'`; its height dragged from its top edge), with one tab per terminal; the external terminal (`terminal_command`) stays available.
- **Open terminal here** from a repo or worktree row's menu, the dependency tree's **Terminal** button or the action palette starts a shell in that folder, its tab named `repo · branch`; with several repos selected, one terminal each.
- **Run command…** (row menu, or *Run command in selected repos* in the palette) runs one command in a terminal of its own on each selected repo (all when none); each tab shows the exit status (`✓`, `✗ code`).

- Colours (the 16 ANSI colours follow the theme), resize, scrollback (wheel, `Shift+PageUp/PageDown/Home/End`), mouse selection (double click: word, triple: line), copy / paste (`Ctrl+Shift+C` / `Ctrl+Shift+V`, `⌘C` / `⌘V` on macOS), `Ctrl+click` opens a URL or an existing file path. While a terminal has the keyboard, the shell gets Ctrl + letter, Alt and plain keys even when the keymap binds them.

## Non-functional requirements

- **Performance:** start < 1 s; dashboard of a 20-repo project < 500 ms; no Git operation ever blocks the UI.
- **Memory (RAM):** a small footprint, unlike Electron clients (GitKraken often reaches 500 MB – 1 GB).
  - Targets: < 150 MB idle with a 20-repo project open; no steady growth over a long session (no leaks).
  - Lazy loading: graph and history loaded per visible window (paged / streamed log); the full history is never held in memory.
  - Inactive projects are unloaded (only a light dashboard summary stays cached).
  - Bounded caches (max size, LRU eviction) for diffs, blobs and stats; stats are computed as a stream and persisted to disk rather than kept in RAM.
- **Aesthetics:** light/dark themes, careful typography, restrained animations, adjustable information density.
- **Themes customizable by a regular user:** no code or file editing required — built-in theme editor with live preview, a full theme derived from a few base colors (background, accent), adjustable fonts / size / density / corner radius, import / export of a readable theme file for sharing.
- **Compatibility:** respects the user's Git config (credentials, SSH, GPG/SSH signing, hooks, LFS).
- **Platforms:** Windows, Linux and macOS (all three in CI); macOS packaging later.
- **Code quality and architecture:** a first-class goal. Code split into single-responsibility modules with interface segregation (small role-based traits); the project must be easy to **customize by anyone who forks it** (extension points, swappable implementations, no core patching needed). Rules: [ARCHITECTURE.md](ARCHITECTURE.md).

## Stack

- **UI:** GPUI (+ `gpui-component`), to be confirmed in Phase 0 by measuring it against a Tauri spike; egui as the fallback. A native UI is preferred because a WebView alone (e.g. WebView2) costs roughly 80–150 MB, which conflicts with the RAM target. Rationale: [PLAN.md](PLAN.md) §2.2.
- **Hybrid Git backend:**
  - **reads** (status, log, graph) through `gitoxide` (`gix`) → fast, parallel across N repos;
  - **writes** (commit, push, rebase) through the `git` CLI → guaranteed compatibility with hooks, credentials and signing.

## Resolved questions

- **GitHub / GitLab integration:** out of v1. Only "open in browser" links (repo, branch, commit, create PR). Full integration is §8 (P2).
- **Submodules:** not added automatically; detected (badge) with an "add submodules to project" action (P1). Nested display as a toggleable tree is §9 (P2).
- **Project file:** a project definition always lives in an `archipel.toml` at a folder root, never in the user data dir. The user data dir only keeps the registry of known projects, personal state (UI state, hidden repos) and app data (caches, undo journal, stats); none of it goes in the shared file.
- **Multi-repo commit:** the same branch is not required; warning when branches differ, plus a per-project "require same branch" option.
- **Distribution:** open source (MIT), signed installers, no telemetry.
- **Adding a repo by cloning** (URL): P1.
